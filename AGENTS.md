# Illustration Composer — контекст и инструкции для Codex

Архитектурный план развития и критерии этапов: [docs/architecture-plan.md](docs/architecture-plan.md). Это план, а не описание уже реализованных функций.

Не считай перечисленные ниже планы уже реализованными.

## 1. Задача и критерии сдачи

Это тестовое задание для позиции Junior AI Developer: сделать сервис, автоматически собирающий иллюстрации из **существующих векторных объектов** исходной Figma-библиотеки (20 иллюстраций). Реализация в виде **Figma-плагина** разрешена и выбрана осознанно; отдельный сайт не нужен.

Обязательные пользовательские сценарии:

1. **По метафоре/заголовку**: пользователь пишет текст («Финансовая безопасность»), система семантически подбирает подходящие **существующие** объекты из каталога и собирает композицию.
2. **По названиям компонентов**: пользователь указывает нужные предметы, система находит их в каталоге и компонуeт.

Функциональные требования:

- использовать исходную библиотеку SVG/Figma-векторов, не генерировать новые предметы;
- сохранять исходную геометрию, векторную структуру, пропорции и возможность редактирования каждого элемента;
- собирать объекты из разных исходных иллюстраций на общий холст; размещать, поворачивать, дублировать, удалять, изменять порядок слоёв (встроенные средства Figma допустимы);
- выбирать формат холста, уровень детализации **S/L**, тип объекта **main/background** (главный/фоновый) и цветовую палитру;
- поддерживать импорт/регистрацию новых палитр и автоматическую перекраску **копий** исходных векторов, сохраняя контуры и исходники;
- экспортировать итоговую композицию в **SVG**, без растрирования итоговых объектов;
- сдать запускаемый проект/демонстрацию, репозиторий, краткое описание архитектуры и перечень AI-инструментов, 2–3 композиции.

**Приоритет — законченный работающий продукт, а не количество функций.**

## 2. Стек и организация репозитория

Монорепозиторий с npm workspaces (`apps/*`, `packages/*`), TypeScript strict, Figma Plugin API, esbuild, Vitest, Node.js. Разработка на Windows / PowerShell.

```text
illustration-composer/
├── apps/
│   └── figma-plugin/
│       ├── manifest.json
│       ├── src/
│       │   ├── code.ts                    # точка входа, Figma API, обработка UI-сообщений
│       │   ├── ui.html                    # HTML/CSS/JS-интерфейс без фреймворка
│       │   ├── figma-library-scanner.ts   # поиск векторных групп в исходной библиотеке
│       │   ├── figma-asset-matcher.ts     # эвристические предложения соответствий
│       │   ├── figma-library-resolver.ts  # определение распознанных/неизвестных ресурсов
│       │   ├── figma-asset-index.ts       # индекс объектов и вариантов
│       │   ├── figma-catalog-factory.ts   # прежняя сборка каталога
│       │   ├── figma-registry-store.ts    # хранение Registry, bootstrap, каталог из Registry
│       │   ├── figma-asset-adapter.ts     # Figma source node -> размеры / векторная копия
│       │   ├── figma-palette-adapter.ts   # перекраска заливок и обводок копий
│       │   └── figma-scene-renderer.ts    # сцена -> Figma Frame
│       └── tests/
└── packages/
    └── core/
        ├── src/
        │   ├── catalog/                # AssetId, VariantId, Asset, AssetCatalog, LibraryRegistry
        │   ├── composition/            # Row / Focus layout
        │   ├── palette/                # ColorPalette, палитры, сопоставление цветов
        │   └── index.ts
        └── tests/
```

Структура — ориентир; наличие каждого файла и его актуальные экспорты **проверяй непосредственно в проекте**, не создавай дубликаты.

Команды из корня репозитория:

```powershell
npm run typecheck -w @illustration-composer/core
npm run test -w @illustration-composer/core
npm run build -w @illustration-composer/core
npm run typecheck -w @illustration-composer/figma-plugin
npm run test -w @illustration-composer/figma-plugin
npm run build -w @illustration-composer/figma-plugin
```

`manifest.json` указывает на `dist/code.js` и `src/ui.html`; esbuild собирает точку входа в IIFE. Сам HTML не собирается esbuild и открывается Figma по пути из манифеста.

## 3. Текущее состояние (не путать с планом)

### Реализовано и проверялось

- Сканирование исходной страницы Figma **«Библиотека компонентов»**, секций **«Размер S» / «Размер L»**; главные и фоновые векторные группы.
- В исходном наборе было обнаружено 40 групп (ориентировочно 10 смысловых объектов × 4 варианта). Изначально 36 вариантов удавалось идентифицировать, 4 оставались с общими именами `Group ...`. **Не присваивать этим четырём автоматически имя «Цветы»**: это догадка, пользователь должен подтвердить тип.
- `Row` и `Focus` — две стратегии компоновки; размеры холста `1200×800`, `1000×1000`, `800×1200`. Изображения создаются как копии исходных Figma-векторных узлов, а не AI-картинки.
- Выбор двух объектов, формата и раскладки через UI; работал в Figma.
- Палитры `original`, `mint`, `peach` и импорт пользовательского JSON: перекрашиваются известные цветовые роли в копиях (`SOLID` fills/strokes), чёрные контуры и нераспознанные цвета остаются. Мятная и персиковая схемы визуально проверены пользователем.
- Core `LibraryRegistry` с `AssetId` и `VariantId`, регистрацией объекта, конфликтом, добавлением альтернативы, явной заменой, переключением активной версии и snapshot. **30 Core тестов проходили** (4 asset + 5 catalog + 5 row + 3 focus + 4 palette + 9 registry).
- Позже передавались файлы интеграции Registry (`figma-registry-store.ts`, обновлённые `code.ts`, `ui.html`, `figma-asset-adapter.ts` и др.); частично сборка проходила. **Интеграция не подтверждена работающей от начала до конца.**

### Известный текущий блокер — исправить первым

Обновление 2026-11-04: хранилище переведено на shared plugin data с миграцией доступной старой приватной записи. Typecheck/test/build прошли (Core: 30 тестов, plugin: 13). Пользователь подтвердил успешный запуск после исправления: описанная ниже ошибка запуска устранена. Сохранение после перезапуска, восстановление вариантов и остальные ручные сценарии ещё не подтверждены. См. [docs/registry-storage-check.md](docs/registry-storage-check.md). Ниже сохранён контекст исходной ошибки.

Сейчас Figma при запуске выдаёт:

```text
in getPluginData: Cannot get private plugin data in a plugin without an ID.
Make sure your plugin manifest has a valid "id" field.
```

Текущий `apps/figma-plugin/manifest.json` был таким (без `id`):

```json
{
  "name": "Illustration Composer",
  "api": "1.0.0",
  "main": "dist/code.js",
  "editorType": ["figma"],
  "documentAccess": "dynamic-page",
  "ui": "src/ui.html",
  "networkAccess": { "allowedDomains": ["none"] }
}
```

Причина: новый `FigmaRegistryStore` обращается к `figma.root.getPluginData()`/`setPluginData()`, где среда запуска требует действительный plugin ID; прежний Composer не использовал этот механизм и работал без ID. **Не утверждать, что проблема решена.**

Задача Codex: сначала изучить реальный `figma-registry-store.ts` и допустимые способы долговременного хранения данных в Figma Plugin API. Предложить и реализовать **самый простой поддерживаемый рабочий вариант** без потери истории, без переименования оригинальных узлов и без дополнительных серверов. Пользователь предпочёл бы не создавать и не регистрировать новый плагин ради этой ошибки; если надёжный документный persistence действительно требует ID, прозрачно объяснить ограничение и предложить минимальную процедуру, а не маскировать ошибку временным хранением. **Не подменять долговременное хранение переменной в памяти.** Учитывать область видимости данных: должны переживать перезапуск плагина, а по возможности быть доступны другим пользователям того же Figma-файла.

Предыдущая TypeScript-ошибка в `code.ts` при `item[property]` (`fills | strokes`) исправлялась через два явных type guard: `"fills" in item && Array.isArray(item.fills)` и аналогично для `strokes`; проверить, что текущая версия компилируется.

## 4. Окончательные архитектурные решения

### Core / Domain

- **Не зависит от `figma`, DOM, API или файловой системы.** Чистый TS, типизированные идентификаторы.
- `AssetId` — идентификатор смыслового предмета, `VariantId` — идентификатор отдельной версии.
- `LibraryRegistry` хранит самостоятельные предметы и их варианты; один предмет может иметь **1, 2, 3, 4 или более вариантов**. Не требовать обязательной четвёрки.
- Вариант имеет `resourceKey`, `size` (`S|L`), `role` (`main|background`) и `active`.
- Разрешены **несколько альтернатив для одного slot (`size+role`)**, но только одна активная. Выбор/восстановление старой версии — явная операция.
- Зарегистрированный `resourceKey` не должен повторно назначаться другому предмету. При конфликте — результат без мутаций, не silent overwrite.
- Для замены передаётся явное решение `replace` и `expectedActiveId`, на сохранении **повторно проверяется** актуальное состояние. Поддержать `alternative` и `cancel`.
- Названия — пользовательские данные; ID не нужно выводить из названий заново после каждого изменения. Нельзя полагаться на единственный `name` как на устойчивый идентификатор.
- Цветовая палитра — **другая сущность**, не предмет и не вариант.

### Infrastructure / Figma

- Источники: оригинальные `GROUP`, при необходимости `FRAME` или `VECTOR`. Копировать в новую сцену, **не перемещать/не менять оригинал**.
- Привязка стабильного доменного `resourceKey` к конкретному Figma `nodeId` — инфраструктурная ответственность.
- Не полагаться на то, что `nodeId` вечен при копировании библиотеки в другой файл; обрабатывать потерянные источники и явно уведомлять.
- Каталог и привязки должны переживать перезапуск. Сохранение обновления и состояние регистрации должны оставаться согласованными.
- Отдельные ресурсы палитры регистрируются с выбранным пользователем названием и цветами; доступные роли сопоставляются осмысленно. Не считать любой цветной рисунок «палитрой».
- Не ломать экспорт SVG и не растрировать основную сцену. PNG допустим **только для миниатюр UI**.
- Типы Figma — через `in`/type guards; избегать `any` и произвольных кастов.

### UX регистрации нового ресурса

При обнаружении нового, пока не зарегистрированного ресурса:

1. Покажи **реальный предпросмотр** (например PNG-миниатюра для UI), источник/слой и текущий статус.
2. Пользователь явно выбирает одну из трёх категорий:
   - **Новый предмет**: задаёт имя и первый вариант (`size`, `role`).
   - **Вариант существующего предмета**: выбирает предмет, `size`, `role`.
   - **Новая цветовая палитра**: назначает цвета палитры по ролям. Это не предмет.
3. Если в целевом предмете слот занят, **покажи оба объекта (старый и новый)** и предложи `Добавить альтернативу / Заменить активный / Отмена`. Не заменять при первом клике «Добавить».
4. При подтверждённой замене **сохраняй прежнюю привязку**, чтобы пользователь мог вернуть её позже; оригинальную Figma-группу не удалять.
5. Запретить двойную регистрацию одного источника, явно предупреждать о конфликте имён и о пропавшем источнике.
6. Пользователь подтверждает смысл ресурса. Никаких автоматических эвристик «оставшиеся четыре группы = Цветы» или «один большой объект = Куст». Эвристика может быть только подсказкой, не фактом.
7. Не заставлять художника переименовывать слои исходного файла ради работоспособности.

## 5. Принципы разработки

- **Не переписывай работающую архитектуру целиком.** Сначала прочитай действующие файлы и найди минимальный путь интеграции.
- Поддерживай Clean Architecture: доменные правила в Core, Figma API в adapter/store, orchestration в `code.ts`, UI — только сообщения и представление.
- **SOLID и KISS обязательны.** Небольшие связные классы и модули с одной ответственностью; чистые функции там, где не нужны состояние и жизненный цикл. Не создавать раздутые сервисы, универсальные менеджеры, базовые классы и интерфейсы ради формального соблюдения архитектуры.
- Зависимости направлены к домену; внешние API подключаются через узкие контракты по реальной необходимости. Предпочитай композицию наследованию. Расширение должно добавлять конкретное поведение без несвязанных изменений в других слоях.
- Размер оценивай по ответственности и связности, без произвольного лимита строк. Не дроби цельную операцию на бессмысленные обёртки. Каждая новая абстракция должна иметь объяснимую пользу для текущего сценария, изоляции внешней зависимости или проверки доменного правила.
- Простой, ясный нейминг, строгая осмысленная типизация, минимальные зависимости, минимум комментариев. Избегай `any`, огромных сервисных классов без необходимости и дублирования логики.
- Используй существующие абстракции `AssetCatalog`, `LibraryRegistry`, `FigmaAssetAdapter`, `FigmaSceneRenderer`, `ColorPalette`.
- Прежде чем менять сигнатуры, найди **все** вызовы и тесты; не допускай несовместимых версий (`FigmaAssetAdapter` уже однажды получил конструктор с одним аргументом при старом вызове с двумя).
- Сохраняй совместимость уже созданных композиций и старых вариантов/палитр, когда это возможно.
- Новые библиотечные ресурсы могут быть неполными: нет S, нет background, только L/main — это валидно. UI должен показывать только доступные варианты либо сообщать об отсутствии.
- Тестируй граничные случаи и конфликты, **не устраивай серию бессмысленных прототипов**. Пользователь попросил работать крупными законченными шагами и довести тестовое до сдачи быстро.
- **Перед внесением изменений** покажи краткий план и реальные затронутые файлы; затем вноси изменения и запускай доступные проверки. Результат описывай конкретно: что изменил, какие команды прошли и какие ручные проверки ещё нужны.
- Пользователь предпочитает **полный готовый код файлов прямо в чате**, когда не используется агент с прямым доступом к репозиторию; Codex при доступе к проекту должен править файлы непосредственно.
- Не говори «готово» про функции, не проверенные сборкой/тестами и, где требуется, запуском Figma.

## 6. Что осталось до полной сдачи — порядок приоритетов

1. **Снять runtime-блокер Registry persistence** и довести интеграцию с Figma до рабочего состояния: регистрацию новых предметов, вариантов и палитр; конфликты, сохранение между запусками, возвращение старой версии; корректный каталог для Composer.
2. **Сценарий 2**: ввод названий нескольких объектов текстом (не только два dropdown), разрешение имён в известные AssetId, понятные ошибки неизвестных названий, автоматическая композиция.
3. **Сценарий 1**: подбор по метафоре/заголовку. AI **только выбирает ID существующих предметов** (и, возможно, их роли/важность), не рисует и не генерирует SVG. Валидируй результат по каталогу. Если используешь внешнюю LLM, не храни API-ключ в плагине: минимальный backend/proxy **только если необходим**; в текущем manifest `allowedDomains: ["none"]`, сетевого доступа нет. Не развертывай тяжёлую инфраструктуру.
4. Поддержка >2 предметов, выбор S/L и main/background, адекватные композиции на вертикальных холстах и для произвольного количества вариантов, корректный порядок слоёв.
5. Удобный экспорт композиции в SVG с сохранением геометрии, редактируемости и палитры; проверить реальный экспорт.

Важно: пока не закрыты оба обязательных сценария, не трать время на косметическую полировку UI или избыточное расширение числа layout-алгоритмов.

## 7. Критерии приёмки

- Плагин устанавливается/запускается из репозитория по понятной инструкции без необъяснённых ошибок.
- Старые предметы доступны; новые ресурсы обнаруживаются и регистрируются пользователем как предмет/вариант/палитра.
- Для `Куст` с единственным `L/main` не требуется создавать искусственные `S/background` и прочие варианты.
- Нельзя перезаписать занятый слот без предупреждения, сравнения и явного подтверждения; можно сохранить альтернативу, восстановить предыдущую версию.
- Регистрация и палитры сохраняются после перезапуска.
- Ручной текстовый ввод названий и ввод метафоры оба создают композицию из **существующих объектов**.
- Исходные иллюстрации не изменяются; объекты на выходе — независимые векторы, SVG экспортируется без raster fallback.
- `typecheck`, `test`, `build` проходят для Core и Figma plugin, а ключевые UI-сценарии вручную проверены в Figma.
- Есть README, исходники в репозитории, демонстрация и 2–3 примера.
