# Registry: хранение и проверка в Figma

## Реализовано в коде

Реестр сохраняется на figma.root через getSharedPluginData/setSharedPluginData.
Namespace: illustrationComposer. Ключ: illustration-composer-registry-v1.
Registry, история вариантов, привязки и зарегистрированные палитры записываются одним JSON.
Это данные документа, а не локальная память пользователя. Shared data доступны другим плагинам; секретов в реестре быть не должно.

При отсутствии pluginId приватный API не вызывается. Если shared-записи нет и доступен исходный pluginId, прежняя приватная запись проверяется и переносится; оригинал не удаляется. При повреждённой записи или ошибке сохранения запуск останавливается с ошибкой, данные не заменяются пустым реестром.

Приватные данные другого plugin ID прочитать нельзя. Если реестр раньше сохранялся под другим ID, для миграции нужен именно прежний ID. В текущем манифесте ID отсутствует; выдуманное значение добавлять нельзя.

Лимит записи проверяется по UTF-8, включая namespace и ключ, с запасом до лимита API 100 kB. Изменений исходных Figma-узлов этот механизм не требует.

Документация API: https://developers.figma.com/docs/plugins/api/properties/nodes-setsharedplugindata/

## Автоматические проверки

2026-11-04: typecheck, test и build обоих workspaces прошли. Core: 30 тестов; plugin: 13 тестов, включая 10 тестов хранилища.

Проверены: отсутствие приватных вызовов без ID, загрузка новым экземпляром store, сохранение истории/привязок/палитр, восстановление варианта и каталог активных вариантов, миграция без удаления оригинала, приоритет shared-записи, ошибки чтения/записи, недопустимые привязки/палитры и размер UTF-8.

Тесты используют имитацию Figma API и не подтверждают поведение настоящей среды запуска.

## Ручная проверка

2026-11-04: пользователь подтвердил, что плагин запускается после изменения хранения. Ошибка getPluginData при запуске больше не воспроизводится. Остальные пункты, включая сохранение после перезапуска и восстановление вариантов, пока не подтверждены.

1. Собрать оба пакета, импортировать apps/figma-plugin/manifest.json через Plugins → Development → Import plugin from manifest в Figma Desktop. Если плагин уже импортирован, запустить его заново после сборки.
2. В файле с исходной страницей «Библиотека компонентов» запустить плагин без добавления id. Ожидается открытие UI без ошибки getPluginData.
3. Убедиться, что известные предметы доступны. Создать прежнюю композицию из двух предметов с исходной и мятной палитрами; проверить, что оригиналы не изменены.
4. Зарегистрировать новый предмет с единственным L/main. Закрыть плагин и открыть снова: предмет и доступный вариант должны сохраниться.
5. Зарегистрировать другой источник в занятый слот: сравнить миниатюры, отменить; повторить и сохранить альтернативу. Активный вариант должен остаться прежним.
6. Выполнить явную замену, перезапустить плагин, активировать старый вариант и ещё раз перезапустить. Обе версии и привязки должны сохраниться, композиция должна использовать активную.
7. Зарегистрировать палитру из выбранного ресурса с назначением цветов; перезапустить и применить её к новой композиции.
8. По возможности открыть тот же файл другим пользователем с правом редактирования и проверить доступность сохранённого каталога через этот плагин.

Для проверки миграции нужен файл с прежней приватной записью и соответствующий настоящий plugin ID. Не удалять записи вручную в рабочем файле ради теста.

## Границы этого шага

Импорт JSON-палитр пока остаётся временным состоянием UI. Поддержка параллельных изменений несколькими пользователями, отдельная группа палитр, подтверждение эвристик bootstrap и предварительное обнаружение потерянных источников ещё требуют реализации. Успешная проверка storage не закрывает весь этап надёжной библиотеки.
