# Illustration Composer — архитектурный план

Дата: 2026-11-04. Статус: согласованное направление разработки; перечисленные этапы ещё не означают реализованный функционал.

**Текущий приоритет пользователя:** автоматически собирать качественные композиции уровня исходных примеров по теме или названиям. Наличие ручных шаблонов и обновлённого UI не закрывает этот результат. Ближайший этап и критерии описаны в [status-and-next-steps.md](status-and-next-steps.md). Технические долги выполняются в самом конце, после продуктовой задачи и художественной проверки; дальнейшая косметика UI сейчас не приоритет.

Ход реализации: первый шаг хранения переведён на shared document data; typecheck/test/build обоих пакетов проходят. Пользователь подтвердил успешный запуск плагина после исправления. Сохранение после перезапуска и остальные ручные сценарии ещё не подтверждены. Подробности: [registry-storage-check.md](registry-storage-check.md). Этап 1 целиком не завершён.

## 1. Цель и границы

Первый планировщик свободной сборки и архитектурное направление отношений/референсов описаны в [automatic-compositions.md](automatic-compositions.md). Разделять фон холста и исходные background-предметы. Разрешённые перекрытия задаются замыслом сцены; запрет всех пересечений не распространяется на сцены с опорой и глубиной. Ввод референса — будущая возможность, а не уже реализованный анализ картинок.

Довести существующий Figma-плагин до требований тестового. Художник вводит названия предметов или метафору, выбирает формат и палитру, получает композицию из исходных редактируемых векторов. Детальные настройки доступны по необходимости.

Обязательны оба текстовых сценария, долговременный каталог, импорт палитр, автоматическая композиция и SVG-экспорт. Перемещение, поворот, дублирование, удаление и ручная перестановка слоёв доступны средствами Figma.

Новые изображения, декоративные SVG-предметы и фоновые фигуры не генерируются. Все иллюстративные объекты, включая фоновые, берутся из исходной библиотеки. Перекраска и пропорциональный масштаб разрешены; исходная геометрия и структура сохраняются. Отдельный сайт не требуется.

## 2. Подтверждённая исходная точка

- Core не зависит от Figma; есть AssetCatalog, LibraryRegistry, Row, Focus и ColorPalette.
- Registry хранит альтернативы и активный вариант каждого доступного слота S/L × main/background. Обязательной четвёрки нет.
- Адаптер клонирует исходные узлы, палитра применяется к копиям.
- UI и orchestration пока рассчитаны на два объекта; текстовые сценарии и собственный SVG-экспорт отсутствуют.
- Запуск блокирует приватное document storage при отсутствии plugin ID.
- Регистрация палитры из узла предусмотрена, импорт JSON живёт только в текущем UI.
- Bootstrap автоматически принимает часть эвристических совпадений; это нужно согласовать с обязательным подтверждением пользователем.
- Проверены typecheck обоих пакетов, 30 Core и 3 plugin теста. Сборка и ручная проверка Figma в рамках анализа не выполнялись.
- Структура и визуальные качества всей библиотеки ещё не обследованы: доступ через Figma MCP ограничен квотой.

## 3. Предметы и палитры — разные сущности

### Предметы

Asset имеет устойчивый AssetId, пользовательское имя, семантические теги/синонимы и варианты. Variant имеет VariantId, resourceKey, size, role и active. Фоновый предмет — полноценный вариант библиотеки с role=background.

### Палитры

Palette имеет собственный ID, имя и отображение цветовых ролей в цвета. Связь с Figma-источником необязательна: JSON-палитра должна сохраняться без sourceNodeId. Палитра не получает AssetId или VariantId и не входит в AssetCatalog.

В UI библиотеки выделяются группы «Предметы», «Палитры», «Неразобранные». Создание композиции показывает предметы отдельно от выбора цветовой схемы.

В исходном Figma-файле поддерживается отдельная служебная секция «Палитры»: она исключается из сканирования предметов. Организация этой секции не должна требовать переименования или перемещения существующих оригиналов. Зарегистрированный ресурс определяется по сохранённой классификации даже вне секции.

Инварианты:

1. Один источник нельзя одновременно зарегистрировать как предмет и как палитру. Проверка действует в прикладной операции сохранения, а не только в UI.
2. Палитры не выдаются поиском названий, не передаются AI как доступные предметы и не принимаются планировщиком/рендерером как объекты сцены.
3. Палитра меняет только разрешённые цветовые роли копий. Чёрные контуры и неизвестные цвета сохраняются.
4. Цветной объект не признаётся палитрой автоматически: категорию и сопоставление ролей подтверждает художник.
5. Импорт JSON и регистрация из Figma создают одну и ту же доменную сущность с одинаковой валидацией и долговременным сохранением.

Запрет относится к выбору и использованию палитр самим плагином. Ручное копирование узлов художником средствами Figma не ограничивается.

## 4. Границы архитектуры

| Слой | Ответственность | Ограничение |
| --- | --- | --- |
| Core / domain | Предметы, варианты, палитры, ограничения сцены, геометрия компоновки | Без Figma, DOM, сети и хранения |
| Application | Разбор ввода, выбор предметов, регистрация, конфликты, создание композиции | Работает через небольшие порты и типизированные команды |
| Figma infrastructure | Сканирование, document storage, привязки узлов, миниатюры, клонирование, перекраска, экспорт | Без семантического выбора по именам слоёв |
| UI | Ввод, предпросмотр, выбор, подтверждение, обратная связь | Не реализует доменные правила и не хранит единственный экземпляр данных |

Сохранить существующие классы и переносить ответственность из code.ts по мере реализации этапов. Не создавать универсальный framework, DI-контейнер или дополнительные пакеты без необходимости. Разделение на слои не требует отдельного npm workspace для каждого слоя.

Общий поток: ввод → список существующих AssetId → выбор доступных вариантов → план композиции → проверка → Figma-рендер → SVG-экспорт. Названия и метафора используют общий путь после выбора предметов.

### SOLID и KISS — обязательные правила реализации

- Небольшие связные классы и модули с одной причиной изменения. Не объединять хранение, подбор, геометрию, рендер и UI в один сервис или универсальный менеджер.
- Чистые преобразования и алгоритмы реализовывать функциями. Класс использовать, когда нужны инкапсуляция состояния, инварианты или жизненный цикл.
- Зависимости направлять к домену. Узкие порты нужны на реальных границах, например для хранения и семантического подбора; внутренней функции не требуется интерфейс и отдельный класс-обёртка.
- Расширять через композицию конкретных стратегий и адаптеров. Не вводить иерархии наследования, базовые сервисы, фабрики и DI-контейнер без подтверждённой необходимости.
- Контракты должны быть небольшими и осмысленными; каждая реализация соблюдает их поведение, включая ошибки. Не заставлять адаптер поддерживать несвязанные операции или заглушки.
- Выбирать простейшее решение, которое закрывает текущие требования и сохраняет границы слоёв. Не строить расширяемость под гипотетические задачи.
- Не измерять архитектуру количеством файлов или произвольным лимитом строк. Разделять по ответственности; сохранять цельную операцию читаемой, не дробить её на бессмысленные обёртки.

При ревью каждого этапа проверять: понятна ли ответственность модуля, направлены ли зависимости внутрь, есть ли практическая причина у каждой новой абстракции, можно ли упростить решение без потери поведения. Успешные тесты не оправдывают раздутую архитектуру.

## 5. Хранение и регистрация

Хранить версионированный документ: Registry, привязки resourceKey → nodeId, палитры и ревизию. Не использовать память или clientStorage как единственный источник реестра.

Первым проверить shared plugin data на DocumentNode с постоянным namespace в реальном запуске без ID. Если этот путь работает, использовать его с проверкой схемы и размера в байтах. При наличии старых приватных данных предусмотреть перенос с сохранением старой записи до успешной проверки новой. Недоступные приватные данные без прежнего ID нельзя считать пустым реестром и молча заменять bootstrap.

Если среда всё же требует действительный ID, описать минимальную процедуру получения ID через Figma; не выдумывать значение и не маскировать проблему временным хранением.

Операции регистрации сохраняют Registry, классификацию и привязки согласованно. Перед подтверждённой заменой перечитывать документ и проверять текущий активный вариант. Очередь одного экземпляра не решает одновременное редактирование несколькими пользователями. Проверка ревизии помогает обнаруживать устаревшее состояние, но без серверной транзакции не обещает полной атомарности между клиентами; это ограничение нужно проверить и описать.

Новый ресурс проходит явную классификацию с реальным предпросмотром. Эвристика даёт подсказку, требующую подтверждения. Занятый слот показывает старый и новый варианты; доступны альтернатива, замена и отмена. История и оригиналы сохраняются.

Пропавшие источники отмечаются в каталоге заранее. Поддержать явную перепривязку сохранённого resourceKey к выбранному узлу без потери истории. Не восстанавливать связь молча по имени или похожим размерам.

## 6. Основной сценарий художника

1. Выбрать «По названиям» или «По метафоре» и ввести текст.
2. Выбрать формат и палитру; остальное получить автоматически.
3. Увидеть выбранные предметы с миниатюрами, затем создать композицию.
4. При необходимости открыть дополнительные настройки: состав, главный предмет, доступные S/L и main/background.
5. Редактировать результат в Figma и экспортировать SVG.

Не требовать регистрации уже известной библиотеки при каждом запуске. Управление ресурсами находится отдельно от основного сценария. Неизвестное название объясняется рядом с вводом с предложением доступных совпадений; неоднозначность не разрешается скрытой заменой.

Недоступные варианты не предлагаются как рабочий выбор. Автоматический выбор размера/роли следует явной политике и отображается пользователю. Для предмета только с L/main не создавать искусственных вариантов.

Показывать состояние обработки, результат и понятную ошибку; повторный клик не должен случайно создавать дубликаты. Сохранять текст и настройки после ошибки. У полей должны быть видимые подписи.

## 7. Подбор по названиям и метафоре

По названиям: нормализация регистра, пробелов и ё/е, разбор нескольких названий, синонимы, разрешение в AssetId, явные неизвестные/неоднозначные совпадения. Учитывать составные названия. Сохранять явно запрошенный состав; дополнительные фоновые предметы добавлять только в понятном пользователю режиме автоматического дополнения.

По метафоре: подбирать главный смысловой объект, поддерживающие и, при наличии подходящих ресурсов, фоновые. Для этого нужны описания/теги каталога; одного имени узла недостаточно.

Порт семантического подбора возвращает только существующие ID и смысловую важность. Ответ проверяется по каталогу и доступным вариантам. Палитры в список кандидатов не входят. Результат можно скорректировать до создания.

Выбор между локальным семантическим механизмом и внешней LLM сделать после проверки качества на примерах задания. Набор жёстких соответствий нескольким фразам не выдавать за универсальное понимание метафор. Если понадобится LLM, ключ хранится вне плагина, сеть разрешается адресно, proxy остаётся минимальным.

## 8. Качество композиции

UX-уточнение: интерфейс предназначен для художника. Стартовый экран — вариация готового шаблона; показываются только реальные сменные предметы выбранной сцены. Пустые и служебные Group/Frame не становятся предметами и сохраняются в копии автоматически. Декоративные контролы создаются только для существующего размеченного декора источника, без добавления новых элементов. Вкладки объясняют своё назначение, сложные параметры раскрываются по необходимости. См. [artist-interface.md](artist-interface.md).

Уточнение 2026-11-04: авторские шаблоны могут намеренно перекрывать предметы — например, телефон лежит на книге. Для шаблонов сохраняются авторские положения и перекрытия, включая замену предмета в существующем слоте. Правило автоматического раздвигания main-предметов ниже применяется к свободной сборке Row/Focus. Явный выбор background по-прежнему помещает предмет позади main. Добавлены все 18 исходных сцен как автоматически доступные шаблоны; устройство набора, наблюдения и дальнейшая модель отношений описаны в [reference-compositions.md](reference-compositions.md).

По запросу пользователя первым практическим шагом этого направления добавлено сохранение готовых векторных сцен как шаблонов расстановки. Предметы верхнего уровня можно явно заменять активными вариантами каталога, сохраняя размещение и слои; фон и декор остаются. Автоматическое назначение предметов по метафоре и художественная адаптация форматов ещё не реализованы. См. [composition-templates.md](composition-templates.md). Работа над шаблонами не означает завершения обязательных текстовых сценариев.

Текущее ограничение шаблонов: менять только общий масштаб сцены вместе с холстом, сохраняя исходное соотношение сторон. Не предлагать новый формат, который фактически оставляет исходную квадратную сцену внутри пустого прямоугольного холста. Декор остаётся сменным слотом с понятной подписью; у предметов отображаются компоновочная роль и исходное название.

Улучшение композиций входит в сдаваемый результат. Приоритет — несколько убедительных сцен, а не большое количество алгоритмов.

Перед изменением layout визуально обследовать исходные иллюстрации: силуэты, пары main/background, размеры, допустимые перекрытия, характерный масштаб, плотность и свободное пространство. Зафиксировать наблюдения и эталонные сцены; не подменять их предположениями по именам и габаритам.

Разделять библиотечную роль варианта main/background и композиционную важность primary/supporting. Это разные признаки: уменьшенный main не становится автоматически background.

План сцены должен явно задавать:

- главный объект и поддерживающие предметы;
- фоновые предметы из библиотеки, когда они доступны и уместны;
- позицию, пропорциональный масштаб, допустимый поворот и порядок слоёв каждого экземпляра;
- безопасные поля и свободное пространство относительно формата;
- контролируемые перекрытия, сохраняющие узнаваемость главного предмета.

По умолчанию фон располагается позади главных объектов. Возможные исключения задаются явно в плане. Не добавлять произвольный фон ради заполнения пустоты. Если подходящего background нет, создавать осмысленную сцену из доступного состава и объяснять ограничение.

Уточнение пользователя: выбранные background-предметы всегда позади main-предметов. В свободной сборке Row/Focus второстепенный main-предмет не должен перекрывать главный: сначала искать свободное место для сдвига в пределах холста, при нехватке места предложить уменьшение до создания результата. Уменьшение выполняется только после явного подтверждения текущего плана. Для авторских шаблонов сохраняются намеренные перекрытия исходной расстановки, включая замену предметов в слотах.

Row сохранить как простую стратегию. Focus развивать до композиции с несколькими поддерживающими/фоновыми объектами и правилами для горизонтального, квадратного и вертикального форматов. Повороты учитывать при проверке границ; не обрезать элементы случайно. Не применять деформацию, случайные украшения или новые тени, меняющие исходный стиль.

Проверять геометрию автоматически, а художественное качество — визуально в Figma. Габаритные прямоугольники не доказывают удачную композицию. Альтернативные раскладки одного состава — последующее улучшение после проверки основной стратегии.

## 9. Этапы и критерии завершения

Ход палитр и экспорта: JSON-палитры сохраняются в документном Registry без привязки к Figma-узлу; импорт вынесен в раздел «Палитры». Добавлен экспорт выбранной сцены в SVG с проверками исходных векторов и повторным импортом во временный узел. Вручную проверены перезапуск с сохранённой палитрой, применение цвета, скачивание SVG 1200×800 и обратный импорт 223 векторных элементов. Добавлены README, JSON-палитра и один проверенный SVG-пример. Подробнее и ограничения — [palettes-and-svg.md](palettes-and-svg.md). Это не означает завершения финальной приёмки всех шаблонов, Registry, чистой установки и демонстрации.

Ход сценария по названиям: реализованы текстовый ввод 1–8 предметов, разрешение имён, сообщения об ошибках и фактических вариантах, сборка через Row/Focus. См. [named-compositions.md](named-compositions.md) для границ и проверок.

Ход сценария по метафоре: добавлен локальный подбор по восьми темам и семантическим профилям существующих AssetId, с объяснениями, проверкой результата и исправлением состава через общий pipeline. Это ограниченный словарный механизм, не универсальная LLM; новые предметы требуют смыслового профиля. В Figma проверены финансовый заголовок с созданием сцены и неизвестная тема с блокировкой создания. См. [metaphor-compositions.md](metaphor-compositions.md). Свободный язык, расширение профилей художником и автоматическое назначение предметов слотам шаблона остаются отдельными задачами.

| Этап | Работа | Критерий завершения |
| --- | --- | --- |
| 1. Надёжная библиотека | Хранение, классификация, отдельные палитры, регистрация, конфликты, потерянные источники | Перезапуск сохраняет предметы, палитры и историю; замена требует подтверждения; старый вариант восстанавливается; палитра не используется как предмет |
| 2. Названия | Несколько объектов, нормализация, синонимы, общая модель запроса и сцены | Ввод нескольких названий создаёт композицию; неизвестные/неоднозначные имена объясняются; предмет с одним вариантом работает |
| 3. Метафора | Семантические данные и подбор через общий pipeline | Разные заголовки дают уместный состав из существующих ID; неверные ID отклоняются; результат можно исправить |
| 4. Композиции | Визуальный аудит библиотеки, фоновые объекты, иерархия, масштаб, слои, адаптация форматов | Проверены 2–3 убедительных сцены, включая сцену с background; нет случайной обрезки и потери главного акцента |
| 5. SVG и сдача | Экспорт, README, архитектура, AI-инструменты, demo, очистка Git | Чистая установка и сборка, оба сценария показаны в demo, SVG проверен повторным импортом, исходники не изменены |

Оба сценария используют уже существующие layouts на первых этапах; полноценную художественную доработку выполнять после их подключения. Косметическое оформление UI не должно задерживать обязательные сценарии.

## 10. Проверки

- Core: конфликты без мутаций, альтернативы/восстановление, неполные варианты, разрешение имён, проверка семантического ответа и геометрии сцены.
- Infrastructure: сохранение/загрузка/миграция, повреждённые данные, классификация источника, пропавшие узлы, ошибка сохранения без изменения принятого состояния.
- Границы: palette ID и ресурс палитры отклоняются в запросе композиции; импортированная JSON-палитра переживает перезапуск.
- Figma: регистрация → конфликт → альтернатива/замена → перезапуск → восстановление; оба текстовых сценария; S/L и роли; три формата; порядок слоёв; независимые редактируемые копии.
- SVG: проверить растровые заливки/узлы до экспорта, сообщить несовместимость, не применять raster fallback; проверить содержимое SVG и повторный импорт. Не обещать точного восстановления Figma-специфичных свойств через SVG.
- Для сдачи выполнить typecheck, test и build обоих workspaces. Удалить отслеживание node_modules, сохранив lockfile и воспроизводимую установку.

## 11. Карта изменений

Существующие точки: packages/core/src/catalog/*, composition/*, palette/*; apps/figma-plugin/src/figma-registry-store.ts, figma-library-scanner.ts, figma-asset-adapter.ts, figma-scene-renderer.ts, figma-palette-adapter.ts, code.ts, ui.html.

Новые прикладные модули и порты добавлять только при выделении конкретных операций. Старые figma-asset-index.ts и figma-catalog-factory.ts проверить по всем вызовам и тестам; убрать дублирование после перехода на единый Registry, сохранив совместимость данных. Точные имена новых файлов определять перед реализацией этапа.

Этот документ фиксирует направление и критерии. Изменение статуса этапа допускается только с указанием выполненных проверок; успешные unit-тесты не заменяют ручной запуск Figma.
